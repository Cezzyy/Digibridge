# CLAUDE.md

Guide for Claude Code in this repo. Read the docs below before changing anything.

## Project

DigiBridge is a web app that measures the digital literacy of ACLC College of Mandaue students in 3 DigComp 2.2 areas, shows each student their level and matching lessons, and gives the research team a dashboard of who is falling behind. Cez is the sole developer; Morales does QA.

- [docs/PRD.md](docs/PRD.md): what to build. Requirement IDs (AUTH-01, ASM-03, ...) are used by tests, commits and bug reports.
- [docs/TRD.md](docs/TRD.md): how to build it: architecture, data model, API, assessment engine, security.
- [docs/Build plan.md](<docs/Build plan.md>): order of work and stage checklists.

## Status

Stage 0. Workspaces, TypeScript, ESLint, Prettier, a Husky pre-commit hook and GitHub Actions CI are set up. `pnpm dev` serves the web app at http://localhost:5173 and the API at http://localhost:8787.

API: an `OpenAPIHono` app with `GET /api/v1/health`, `GET /api/v1/me` (staff always get no respondent or attempt, even one left from before their role changed, so the web gives them the preview) and `POST /api/v1/respondents` (online only for now, respondent role only: consent, general profile and show-identity choice in one insert; 400 for school fields or an old notice version, 403 for staff, 409 if the account already has a respondent) and `POST /api/v1/attempts` (picks 4 basic, 4 intermediate and 2 advanced active items with 4 choices per area through `lib/pick-items.ts`, shuffles items and choices with `lib/shuffle.ts` (Fisher–Yates on `crypto.getRandomValues`), sets `expires_at`; the insert reads the respondent again `for share` as a subquery, so a rejoin that changed their token first leaves `respondent_id` null (401); 201 for a new attempt, 200 with the one in progress, 409 with no profile, after a submitted or expired attempt, or when an area has too few active items), `GET /api/v1/attempts/{id}` (items and choices in the attempt's order, without right answers or difficulty, plus saved answers, `expires_at` and server time), `PUT /api/v1/attempts/{id}/answers/{questionId}` (upsert under a `for share` lock on the attempt; 400 for an item outside the attempt or a choice of another item, 409 once closed or past `expires_at` + `ANSWER_GRACE_SECONDS`) and `POST /api/v1/attempts/{id}/submit` (scores with the pure `lib/scoring.ts` under a `for update` lock through `scoreAndClose` in `lib/close-attempt.ts`: answer points, `area_results` and the overall score and level in one transaction; a late submit closes as `expired` at `expires_at`; a second call returns the closed attempt; 409 if voided; `results_token` comes with the QR code item) and `GET /api/v1/attempts/{id}/result` (overall and per-area points, percentage and level, each area's lesson tiers from `LESSON_TIERS_FOR_LEVEL` with the published lesson or `null`, `resultsToken`, `susAnswered`; never per-item marks; 409 while in progress or voided) and `POST /api/v1/attempts/{id}/sus` (the 10 SUS answers, 1 to 5 in statement order, checked by `susAnswersSchema`; scores them with the pure `lib/sus.ts` and saves one `sus_responses` row under a `for share` lock on the attempt, so a void can't slip in between; 201 with the score, 409 `already_answered` once answered (the primary key keeps one per attempt), 409 `conflict` in progress or voided), all for the respondent themselves (online with the respondent role, or a school-link student's token), with 404 for an attempt that isn't the caller's. Admin (`routes/admin.ts`, `handlers/admin.ts`): `GET /api/v1/admin/overview` (staff: respondents by mode, attempts in progress and finished, open and total school links), and admin only `GET /api/v1/admin/links` (newest first, each with its creator, response count (the respondents who joined through it, voided attempts included) and status from `linkStatus` in `packages/shared`: closed, expired, full or open), `POST /api/v1/admin/links` (`schoolLinkSchema`: school, label, optional course, year level and response limit, and `expiresOn`, the last day open; `expires_at` is midnight after it in Manila through `linkExpiresAt`; the code comes from `lib/link-code.ts`, 10 characters from `LINK_CODE_ALPHABET`) and `POST /api/v1/admin/links/{id}/close` (sets `closed_at` once, and leaves an expired link expired; 404 for an unknown link). Staff, in `routes/admin-respondents.ts` and `routes/admin-stats.ts`: `GET /api/v1/admin/respondents` (paged by `RESPONDENTS_PAGE_SIZE`, the dashboard filters plus status, a search on shown names and student numbers, and the sort; a respondent with `show_identity` false comes with a null name and student number and `identityHidden`, and is never searched or sorted on), `GET /api/v1/admin/respondents/{id}` (profile, their attempt (the one not voided, else the latest voided), area results and SUS answers; for admins only, the answer sheet: every item in the order shown, with its choices, the pick and the right one) `DELETE /api/v1/admin/respondents/{id}` (admin only, USR-03: the respondent with their attempts, answers, area results and SUS through the cascades; an online respondent's profile stays; 204, 404) and `POST /api/v1/admin/attempts/{id}/void` (admin only: `voidAttemptSchema`, a reason and a note required with `other`; one `UPDATE … WHERE status <> 'voided'`, which waits on submit's and answer saves' locks, with a CTE that gives a school respondent the hash of a token nobody holds, so whoever took it can't start again from that browser and the student joins the link again to start over; answers and scores stay; 404, 409 once voided), and `GET /api/v1/admin/stats` (summary cards, levels overall and per area, the SUS mean, spread and statement averages, and average scores by `groupBy`, worked out by the pure `lib/stats.ts`). Admin only, in `routes/admin-items.ts`: `GET /api/v1/admin/items` (item analysis: per question how many saw it, got it right or left it blank, picks per choice, and `itemFlags`). Admin only, in `routes/admin-lessons.ts` (the lessons editor, CMS-04): `GET /api/v1/admin/lessons` (every lesson, drafts too, by area order and tier, the published one first), `GET /api/v1/admin/lessons/{id}`, `POST /api/v1/admin/lessons` (`lessonSaveSchema`: `lessonInputSchema` plus `replaces`) and `PATCH /api/v1/admin/lessons/{id}` (any of its fields, under a `for update` lock): saving a lesson as published first unpublishes the one published for that area and tier, in the same transaction, so `lessons_one_published_per_tier_idx` holds, and that must be the lesson `replaces` names (null for none; the editor sends the one it asked about), else 409; the area id rides in the statements as a subquery (`areaIdOf`), so an area never seeded fails `area_id`'s NOT NULL, a 404; a slug in use, or a publish racing another for the same place, is a 409 through `uniqueViolation` in `lib/pg-errors.ts` (with `notNullViolation`; the constraint or column name from postgres.js or PGlite); `DELETE /api/v1/admin/lessons/{id}` deletes drafts only (204; 409 for a published lesson). The dashboard filters become SQL in `lib/dashboard-filters.ts` (`dashboardConditions`, `ageAtConsent`, `currentAttempts`); scores count finished attempts (submitted or expired) only, and the school link filter and column use `respondents.school_link_id`, so a school respondent who hasn't started shows their link too. School links, with no sign-in (`routes/links.ts`, `handlers/links.ts`): `GET /api/v1/links/{code}` (any letter case; the school, label and course and year-level lock; 404 for an unknown code, 410 `gone` with `LINK_GONE_MESSAGES` when closed, expired or full; with the `X-Respondent-Token` of a student who joined that link, their respondent and attempt whatever the link's status, 401 for a token that isn't for this link) and `POST /api/v1/links/{code}/respondents` (`schoolRespondentSchema`: the school profile, identity choice and the school notice's version; under a `for update` lock on the link it checks it's open, counts the respondents who joined it against the limit, checks `linkLockIssues`, and inserts a `mode = school` respondent with `school_link_id`; 409 for a used student number, across all links, unless every attempt under it was voided: then that respondent row, locked `for update` before the check, takes the new profile, consent, link and token (`onlyVoidedAttempts`), and a full link they already count on lets them back in (`rejoiningHere`); returns the respondent token once, 32 random bytes in base64url from `lib/respondent-token.ts`, saving only its SHA-256 hash in `access_token_hash`). A student counts against the link from the profile on and can finish even after the link closes. The attempt routes take the `respondent` middleware (`middleware/respondent.ts`): `X-Respondent-Token` (it wins when both are sent) or a Google sign-in with the respondent role (`authenticate` in `middleware/auth.ts`); it sets `c.var.respondentKey` (`RespondentEnv` in `env.ts`), and handlers match the respondent by profile or token hash with `respondentIs` from `lib/respondent.ts` inside their own query, so no extra round trip; a token that finds no one gets 401 at start and 404 on an attempt. The new attempt copies the respondent's `school_link_id`. Public, with no sign-in: `GET /api/v1/lessons` (published lessons by area order, then tier, filterable by `area` and `tier`) and `GET /api/v1/lessons/{slug}` (the whole lesson: Markdown body, image, video link, resources; 404 for a draft too). The Worker's `scheduled` handler in `index.ts` (cron `*/5 * * * *` in `wrangler.toml`) runs `closeExpiredAttempts`, which scores and closes as `expired` every attempt still in progress past `expires_at` + `ANSWER_GRACE_SECONDS`, one transaction each, skipping rows a submit has locked. The spec at `/api/openapi.json` and the docs page at http://localhost:8787/api/reference. `middleware/` has CORS (only `WEB_ORIGIN`), `db` (sets `c.var.db` from `createDb(env)` on every `/api/v1` request), `auth` (verifies the Supabase token with `jose` against the project's ES256 JWKS, then loads or creates the profile through `lib/profile.ts` and sets `c.var.profile`), `requireRole(...roles)` and the error handler: every error is `{ error: { code, message } }`, thrown as `new ApiError(code, message)`; routes list error responses with `errorResponse()` from `openapi/`. A route that needs sign-in puts `middleware: [auth, requireRole(...)] as const` and `security: [{ Bearer: [] }]` in its `createRoute`, and its handler is typed `RouteHandler<typeof route, AuthEnv>`. Route tests are in `apps/api/src/test/`, one file per area (`app` for health, errors, CORS and the docs, `auth`, `respondents`, `attempts`, `cron` through `worker.scheduled`, `results`, `sus`, `links`, `lessons`, `admin`, `admin-respondents`, `admin-stats`, `admin-items`, `admin-lessons`, `database` for the schema's checks, and `seeds`, which loads the dev question seed and checks its mix, and the lessons seed and checks it fills every area and tier; `pnpm --filter api test`), with `helpers.ts` for the test database, signed-in users, school links and `addQuestionBank()` (the 3 areas with exactly the 4/4/2 mix), and `fixtures.ts` for what more than one file uses (`get`, `send`, `respondent`, `started`, `save`, `submit`, `addSchoolRespondent`, `lessonRow`, ...). `clearAccounts` empties `questions` too (`created_by` points at profiles), so add the bank in `beforeEach`, or call `useQuestionBank()`. The router guard drops Google's `?code=`/`?error=` leftovers from the URL, and moving to another page closes the error screen (in `afterEach`, so a link to the page already open closes it too). `AccountControls` (picture, name, Sign out) sits in both `AppHeader` and `ErrorScreen`'s top bar, so signed-in users can sign out from every page. Every Sign out button (`AccountControls`, `SideMenu`, the declined notice) calls `askSignOut` from `composables/useSignOut.ts`, which opens the one `SignOutDialog` in `App.vue` (the shared `components/ConfirmDialog`, Cancel focused; during the assessment it says the timer keeps running), so a misclick doesn't sign anyone out; only the account-failed error screen signs out at once.

Database: the full schema (11 tables, 8 enums, RLS on every table; `mode` is `online` or `school`; `respondents_school_fields_by_mode` keeps student number, course, year level, `access_token_hash` and `school_link_id` on school rows only; `school_links` replaced `kiosk_sessions`; `respondents.school_link_id` (school rows only, indexed) is the link the student joined through, and `attempts.school_link_id` copies it; a voided attempt has `void_reason_code` (the `void_reason` enum), `voided_at` and `voided_by`, with the note in `void_note`, which `attempts_void_fields_by_status` and `attempts_void_note_for_other` check) is in `packages/db/src/schema` and pushed to Supabase as `supabase/migrations/*.sql`; `packages/db/seed/dev-questions.sql` loads the 3 areas and 39 practice items (5 basic, 5 intermediate, 3 advanced per area, IDs starting `de000000-`), run once in the Supabase SQL editor; `packages/db/seed/lessons.sql` loads 9 published starter lessons (one per area and tier, IDs starting `de000000-`), run after it, and skips any area and tier that already has a published lesson; the enum values come from `packages/shared/src/enums/values.ts`. `packages/shared/src` has one folder per topic, each with an `index.ts` that re-exports it: `enums/` (the enum values, their Zod schemas and labels, `STAFF_ROLES`, `VOID_REASONS` and `VOID_REASON_LABELS`), `errors/` (the API's error codes), `links/` (school links: `schoolLinkSchema`, `LINK_STATUSES` and labels, `linkStatus`, `linkExpiresAt`, the code alphabet and length, `LINK_GONE_MESSAGES`, `linkLockIssues`, and `RESPONDENT_TOKEN_HEADER` with the token's shape), `consent/` (the online and school privacy notices, each with its `version`, saved with each respondent: bump it whenever the text changes; both use the same section titles, which `NOTICE_ICONS` keys on; the school one keeps data `SCHOOL_DATA_KEPT_DAYS`, generic wording for now), `dashboard/` (the dashboard filters `dashboardFiltersSchema`, age groups, respondent statuses, sorts and list query, `HIDDEN_IDENTITY`, `voidAttemptSchema` with `VOID_NOTE_MAX_LENGTH`, stats groupings and query, and item analysis thresholds and `itemFlags`), `lessons/` (slug and resource schemas, `levelsForLessonTier`, the editor's `lessonInputSchema` with its length limits, and `slugFromTitle`), `profile/` (the general profile schema for both modes, date of birth with `ageOn`, `birthDateRange` and `todayInPhilippines` (ages count in Philippine time), full name rules (letters, first and last name) and `schoolProfileSchema`, which adds the school details, `onlineRespondentSchema` for `POST /respondents`, student number regex, courses and their year levels, devices, internet access) and `assessment/` (assessment rules, scoring weights, level cut-offs, lesson tiers per level, and the SUS constants, statements (Brooke's wording in plain English, a placeholder until the team's final text), answer labels and `susAnswersSchema`), with Vitest tests (`pnpm --filter @digibridge/shared test`). Other folders hold a placeholder `index.ts`.

| ----------------- | ------------------------------------------------------------------------- |
| `apps/web`        | Vue 3 SPA, deployed to Cloudflare Pages                                   |
| `apps/api`        | Hono + OpenAPI on Cloudflare Workers; the only code that touches Postgres |

At the root: `tsconfig.base.json` (shared TypeScript settings; every package's `tsconfig.json` extends it with `../../tsconfig.base.json`), `eslint.config.ts` (one lint config for the repo, rules from `packages/config`), `.prettierrc`, `turbo.json`, and `pnpm-workspace.yaml` (workspaces and the version catalog). `.husky/pre-commit` runs lint-staged (its config is the `lint-staged` key in the root `package.json`). `.github/workflows/ci.yml` runs on every push to `main` or `develop` and every pull request: Format, Lint, Typecheck, Test and Build as separate jobs (Turbo cache kept between runs), plus Dependency audit (`pnpm audit --audit-level high`), Secret scan (gitleaks) and Workflow lint (actionlint). Every job installs through `.github/actions/setup`.

## Rules

- TypeScript everywhere, including config files (`eslint.config.ts`, `vite.config.ts`, `drizzle.config.ts`). No `.js` or `.mjs` files.
- Build each feature in the Build plan's order: schema, shared types, route contract, handler, bind in `app.ts`, tests, web composable, page, ship check.
- Work in small steps and check with the user before starting the next stage.
- The browser talks to Supabase only to sign in. Everything else goes through the API, which checks the role on every route.
- Scoring numbers, enums and option lists live in `packages/shared`. Don't hard-code them anywhere else.
- School details (student number, course, year level) belong to school links only. Online mode (public Google sign-in, landing and sign-in pages) is general: it never asks for or shows them, and the API refuses them. Online is one attempt per Google account; school links are one per student number across all links. Only admins make school links.
- `apps/web` imports only types from `apps/api` (`import type`), never runtime code.
- Internal packages are used as TypeScript source (`exports` point at `src/*.ts`), with no build step.
- A dependency used by more than one package gets its version in the `catalog:` in `pnpm-workspace.yaml`.
- Secrets never go in the repo, only `.env.example` and `.dev.vars.example`. Local values live in `apps/web/.env`, `packages/db/.env`, `apps/api/.dev.vars` and `apps/api/.env`. Add a new API variable to `.dev.vars.example` and the `Bindings` type in `apps/api/src/env.ts`.
- User-facing text is plain English, written for students.

## Versions and gotchas

- TypeScript is pinned to `~6.0`, because typescript-eslint supports only below 6.1. TS 6 defaults `types` to `[]`, so list the types each tsconfig needs. `baseUrl` is deprecated; use `paths` on its own.
- Use Vitest 4.1, not 5: Vitest 5 doesn't support Node 25.
- Use `postgres` (postgres.js) 3.4.x. 4.0 was only days old on 2026-10-31.
- pnpm 12 holds back versions published in the last day (`minimumReleaseAge`). Approve packages that need install scripts with `pnpm approve-builds`.
- ESLint loads `eslint.config.ts` through `jiti`, a root devDependency.
- `web` type-checks with `vue-tsc`, not `tsc`, so `.vue` files are checked.
- API routes live under `/api/v1`; the spec and docs page stay at `/api`. Define each route with `createRoute` in `routes/` and bind it to the `v1` app with `.openapi()` in `app.ts`, so it shows up in `/api/reference`.
- To name a `packages/shared` schema in the OpenAPI spec, use `.meta({ id: 'Name' })`, not `.openapi('Name')`: Zod 4 adds methods to each schema when it's built, and shared schemas are built before `@hono/zod-openapi` adds `.openapi`, so they don't have it.
- The API's bindings are in `wrangler.toml`: `HYPERDRIVE` (config `digibridge-db`, Supabase direct connection) and `MEDIA` (private R2 bucket `digibridge-media`, images served by the API). `wrangler dev` connects `HYPERDRIVE` to `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` in `apps/api/.env` and uses a local stand-in for R2. The API type-checks against `@cloudflare/workers-types`, not DOM.
- Deploy with `pnpm --filter <app> run deploy`, not `pnpm --filter <app> deploy` (that's pnpm's own `deploy` command). Pages is a direct-upload project, so pushing to `main` doesn't deploy the web app. The API's public settings are `[vars]` in `wrangler.toml`; its secrets are set with `wrangler secret put`. The web's production `VITE_API_URL` is in `apps/web/.env.production` (gitignored).
- `api`'s `build` is `wrangler deploy --dry-run --outdir dist`: it bundles the Worker without deploying.
- `compatibility_date` in `wrangler.toml` can't be later than the installed workerd supports (2026-10-23 for wrangler 4.156).
- lint-staged 17 needs Node 22.22.1 or newer, which sets the root `engines.node`. Its config lives in `package.json` because lint-staged only loads a `.ts` config when passed `--config`.
- `pnpm install` runs the root `prepare` script (`husky`), which points Git at `.husky/`. CI sets `HUSKY=0` to skip it.
- CI uses Node 25 to match local dev. Bump `node-version` in `.github/actions/setup/action.yml` when local Node changes.
- The Secret scan job runs the gitleaks CLI (version and SHA-256 pinned in `ci.yml`) over the full history, not `gitleaks/gitleaks-action`: the action scans `<first pushed commit>^..<head>`, which fails when a push includes the repo's first commit.
- drizzle-kit writes migrations to `supabase/migrations` with `migrations.prefix: 'supabase'`, so file names match the Supabase CLI's `<timestamp>_name.sql`. Drizzle's snapshots sit in `migrations/meta/`, which the CLI skips. Don't hand-edit pushed migrations; don't use `drizzle-kit push`.
- The Supabase CLI is the root devDependency `supabase` (run it as `pnpm exec supabase`). `supabase link` stores the project ref in `supabase/.temp/`, which is gitignored, so each machine links once.
- Every table calls `.enableRLS()` and has no policies, so the publishable key can't read or write anything. The API connects as `postgres`, the table owner, which skips RLS. Add `.enableRLS()` to every new table.
- `profiles.id` references `auth.users(id)` through `authUsers` from `drizzle-orm/supabase`. Don't export `authUsers` from the schema, or drizzle-kit will try to create it.
- Route tests run on PGlite (in-memory Postgres): `vitest.config.ts` has two projects, `unit` (`src/lib`) and `routes` (`src/test`), and the routes project's setup file, `src/test/setup.ts`, mocks `config/db` so `createDb` returns the test database, which `setUpDatabase()` builds from the real migrations plus a stub `auth.users`, and empties the accounts after each test. The routes project sets `isolate: false`, so the files in a worker share one database (built once): every test must leave it as it found it (`clearAccounts` after each, `clearQuestionBank` after a file that adds the bank). `serveTestJwks()` stubs `fetch` so `jose` gets a test key, and `signedIn(role)` returns headers for a user with that role. Don't import `app` in `test/helpers.ts`: the `config/db` mock imports that file.
- `web` type-checks the API's source through `AppType` (`import type { AppType } from 'api/src/app'`) without Worker globals, so files that `app.ts` reaches import Worker types from `@cloudflare/workers-types` (as `env.ts` does for `Hyperdrive` and `R2Bucket`) instead of using the globals.
- `ADMIN_EMAILS` applies only when a profile is first created, and only if Google marks the email verified. After that only an admin can change a role. Sign out uses `scope: 'local'`, so a facilitator stays signed in on their other devices.
- The Worker runs in `aws:ap-south-1`, the Supabase project's region (`[placement]` in `wrangler.toml`), so each query is a short hop; at the Manila edge every round trip cost ~110 ms. Keep round trips few anyway: postgres.js starts with an empty statement cache on each request's client, so every query with parameters takes two (describe, then execute), and each new connection adds one for `fetch_types`. Run independent queries with `Promise.all`, and prefer one statement (like `INSERT … SELECT … FOR SHARE` in `saveAnswer`) to a transaction of several.
- Call `createDb(c.env)` once per request: a Worker can't reuse a connection across requests, and Hyperdrive does the pooling. postgres.js needs `nodejs_compat` in `wrangler.toml`.
- `db:push` and `db:status` need `supabase link` (which needs `supabase login`). Without a link, pass the URL: `pnpm exec supabase db push --db-url "$DATABASE_URL"` with `packages/db/.env` loaded.
- `DATABASE_URL` uses the session pooler (port 5432). The transaction pooler (6543) doesn't support prepared statements.
- `pnpm audit` reports one moderate advisory (`minimatch`, pulled in by ESLint, dev only). CI fails only on high or critical ones.
